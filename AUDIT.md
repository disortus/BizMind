# Архитектурный аудит проекта BizMind (Конкурсная версия vs Учебный MVP)

> **Дата аудита:** Октябрь 2026  
> **Цель аудита:** Фиксация фактического состояния конкурсной кодовой базы, выявление ограничений, моков и уязвимостей, проектирование целевой архитектуры для полноценного учебного MVP в рамках дисциплины «Проектирование программного обеспечения».  
> **Ветка аудита:** `feature/educational-mvp` (ответвлена от `main`, коммит `1e67b0e`).

---

## 1. Общее резюме состояния системы

Конкурсная версия BizMind представляет собой работающую демонстрационную систему, созданную для презентации ключевой идеи B2B SaaS-аналитики для HoReCa (на примере кофеен «Cafe Aroma» и «Daily Cup»). 

### Ключевые сильные стороны первоначальной реализации:
1. **Реальная база данных и ORM:** Используется SQLite через SQLAlchemy 2.0 с настроенными связями (`relationship`) и каскадным удалением.
2. **Рабочий импорт Excel (.xlsx):** Библиотеки `pandas` и `openpyxl` реально читают бинарные файлы, распознают русскоязычные заголовки и сохраняют записи в базу данных.
3. **Строгая изоляция организаций в существующих эндпоинтах:** Переключение между Cafe Aroma и Daily Cup через заголовок `X-Organization-Id` изолирует выборки в БД (проверено 7 автотестами `pytest`).
4. **Качественный UI:** Современный адаптивный интерфейс на React 19 + Tailwind CSS в темной теме, с графиками Recharts и мобильным меню.

### Критические ограничения и недостатки для учебного MVP:
1. **Отсутствие аутентификации и проверки прав (RBAC):** Авторизация сведена к передаче заголовка `X-Organization-Id`. Нет паролей, хеширования, токенов сессий, а также проверки ролей (Owner, Manager, Employee). Любой клиент может подставить чужой ID организации.
2. **Хардкод контрольной даты:** В `dashboard_service.py`, `forecast_service.py` и `seed_data.py` контрольная дата зашита жестко: `date(2026, 10, 14)`. При отсутствии данных в этот день графики пустеют или генерируют искусственные фоллбэки.
3. **Фоллбэки и искусственные числа:** 
   - В `dashboard_service.py` потенциальная экономия при нулевом результате подменяется константами: `41350.0 if org_id == 1 else 15500.0`.
   - В `forecast_service.py` при отсутствии истории закупок среднесуточный расход принудительно задается как `0.5`.
   - В `PurchasesPage.tsx` в карточке метрик захардкожен текст: «Кофе Espresso Blend (+15%)».
4. **Неполноценный CRUD:**
   - Финансы: есть только создание и список. Нет редактирования, удаления и детального просмотра.
   - Товары: нет эндпоинтов создания, редактирования, архивации и управления SKU.
   - Поставщики и предложения: нет интерфейса создания/редактирования контрагентов и прайс-листов.
   - Закупки: реализованы как плоские архивные строки (`Purchase`), нет бизнес-процесса заказа (статусы Draft $\rightarrow$ Confirmed $\rightarrow$ Received $\rightarrow$ Cancelled).
5. **Отсутствие складского учета (движений):**
   - Остаток товара (`current_stock`) хранится как статичное число в таблице `products`. Нет журнала складских движений (приход, списание, инвентаризация/корректировка).
   - При «закупке» остаток на складе не обновляется автоматически через складской ордер.
6. **Отсутствие аудита действий (Audit Log):** Значимые операции (изменение цен, удаление транзакций, списание остатков) нигде не протоколируются.
7. **Отсутствие экспорта данных:** Нет выгрузки финансовых отчетов, складских остатков и реестров закупок в CSV/Excel.
8. **Типы данных для финансов:** Денежные суммы хранятся как `Float`, что чревато ошибками округления IEEE 754 при финансовых вычислениях.

## 3. План реализации учебного MVP

### Фаза 2: Архитектура и схема данных
1. Расширение моделей SQLAlchemy:
   - `User`: добавление `password_hash`, `role` (owner, manager, employee), `is_active`.
   - `Organization`: добавление настроек (порог алертов, валюта, email, адрес).
   - `Product`: добавление `sku`, `description`, `is_active`, `unit_ratio`.
   - `Supplier`: добавление `phone`, `email`, `address`, `notes`, `is_active`.
   - `SupplierOffer`: добавление `valid_until`, `is_active`, связь с историей цен `PriceHistory`.
   - `PurchaseOrder` и `PurchaseOrderItem`: статусная модель закупки (`draft`, `confirmed`, `received`, `cancelled`).
   - `InventoryMovement`: движения склада (`receipt`, `write_off`, `adjustment`) с фиксацией пользователя и документа-основания.
   - `ActivityLog`: журнал аудита важных действий.
2. Сохранение обратной совместимости с существующей конкурсной схемой и тестами.

### Фаза 3: Аутентификация, RBAC и изоляция
1. Реализация безопасного хеширования паролей (PBKDF2/SHA-256 или bcrypt).
2. Защита эндпоинтов: проверка принадлежности объектов организации вызывающего пользователя.
3. Сохранение быстрого демо-входа для преподавателя/комиссии.

### Фаза 4: Бизнес-логика и API
1. Полноценный CRUD финансов с защитой от двойного учета закупок.
2. CRUD каталога товаров и справочника поставщиков.
3. Процесс закупки: оформление $\rightarrow$ подтверждение $\rightarrow$ приемка с автоматическим созданием складского прихода.
4. Складские списания и инвентаризация.
5. Честное прогнозирование: расчет только при наличии данных, статус «недостаточно данных».
6. Динамические уведомления по правилам.
7. Экспорт данных в CSV/Excel и генератор шаблонов.

### Фаза 5: Пользовательский интерфейс (Frontend)
1. Модальные окна и экраны CRUD для товаров, поставщиков, заказов и финансов.
2. Устранение всех захардкоженных строк в интерфейсе.
3. Экран управления складом и складскими движениями.
4. Экспортные кнопки и загрузка шаблонов для импорта.
5. Информативные пустые состояния (empty states) с пошаговыми подсказками.

### Фаза 6: Тестирование, Docker и документация
1. Расширенный набор тестов `pytest` (авторизация, изоляция, CRUD, склад, заказы, импорт, экспорт).
2. Обновление документации (`README.md`, `BIZMIND_GUIDE.md`, `USER_SCENARIOS.md`, `DEPLOYMENT.md`, `TESTING.md`).
3. Проверка запуска через Docker Compose с сохранением томов.

## 4. Фактические результаты реализации (Учебный MVP завершен)

В рамках работы на ветке `feature/educational-mvp` все замечания аудита были полностью устранены:

| Проблема аудита | Статус в MVP | Что сделано |
|---|---|---|
| 1. Отсутствие аутентификации и RBAC | **Устранено** | Внедрен модуль `security.py` с PBKDF2-HMAC-SHA256, модель `User` расширена ролями (Owner, Manager, Employee), эндпоинты защищены проверкой ролей и принадлежности организации в `deps.py`. Быстрый вход сохранен для демонстрации. |
| 2. Хардкод даты `2026-10-14` | **Устранено** | Во всех сервисах (`DashboardService`, `ForecastService`, `ComparisonService`) контрольная дата вычисляется динамически относительно текущей даты или последней имеющейся в БД операции. |
| 3. Статические фоллбэки экономии | **Устранено** | Фоллбэки `41350.0` и `15500.0` полностью удалены. Потенциальная выгода вычисляется строго из фактических офферов поставщиков в БД. Если данных нет, возвращается честный ноль. |
| 4. Неполноценный CRUD | **Устранено** | Реализован полный CRUD для финансов (`PUT /finances/{id}`, `DELETE /finances/{id}`), товаров (`POST/PUT/DELETE /products`), поставщиков и предложений (`/suppliers/{id}/offers`). |
| 5. Плоские архивные закупки | **Устранено** | Создан модуль заказов `OrderService` со статусной моделью (`draft` $\rightarrow$ `confirmed` $\rightarrow$ `received` $\rightarrow$ `cancelled`), генерацией печатных накладных (`/orders/{id}/document`) и запретом недопустимых переходов. |
| 6. Отсутствие складских движений | **Устранено** | Создана таблица `inventory_movements` и сервис `InventoryService`. Приемка заказа автоматически оприходует сырье на склад. Реализованы операции инвентаризации и списания брака с фиксацией причин. |
| 7. Риск двойного учета расходов | **Устранено** | Создание финансовой транзакции при приемке заказа маркируется `purchase_order_id` и `source: purchase_order`. Финансовый сервис отслеживает происхождение операций. |
| 8. Ложный прогноз при нулевых данных | **Устранено** | В `ForecastService` при отсутствии истории расхода возвращается статус `insufficient_data` с понятным текстовым пояснением вместо фиктивных цифр. |
| 9. Отсутствие аудита действий | **Устранено** | Создана таблица `activity_logs` и функция `log_activity()`. Все критические операции (создание заказов, приемка, инвентаризация, списания, смена настроек) протоколируются с автором и JSON-деталями. |
| 10. Отсутствие экспорта данных и шаблонов | **Устранено** | Добавлены эндпоинты экспорта в Excel и CSV для финансов (`/finances/export`), остатков склада (`/inventory/export`), а также генераторы чистых шаблонов таблиц (`/import/templates/{type}`). |
| 11. Отсутствие валидации строк импорта | **Устранено** | В `ImportService` реализована построчная проверка с фиксацией номеров некорректных строк и подробными объяснениями ошибок. |
| 12. Статичные уведомления | **Устранено** | В `NotificationService` реализован генератор алертов по бизнес-правилам (остаток < min, скачок цены > threshold, черновики заказов) с защитой от спама и дублирования. |

Все 18 автоматических тестов (`tests/test_isolation_and_demo.py` и `tests/test_educational_mvp.py`) пройдены успешно. Фронтенд собран с 0 ошибками TypeScript. Ветка `main` и конкурсный Render-деплой сохранены в 100% исходном состоянии.
